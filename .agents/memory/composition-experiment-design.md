name: Composition experiment design
description: Fair live comparisons of adviser delegation and consolidated Orchestrator skills.
---

Exercise the entire isolated adapter offline before making live comparison calls, including private advisory MIDI materialization/loading and the actual production writer contract.

**Why:** Early comparison attempts stopped on missing experiment capabilities and unequal response budgets before musical generation. Such failures measure the harness, not the orchestration architecture.

**How to apply:** Freeze executed source and imported module hashes before launch. Keep failed setup evidence separate. Match equivalent completion allowances and shared repair budgets, preserve provider finish/usage metadata, and use a common independent assessment rather than comparing self-approval rates.

Offline experiment fixtures must inspect the actual outbound contracts and loaded skill text, not only feed scripted successful responses through validators.

**Why:** A scripted model bypassed an omitted planner response schema, and a copied verification skill retained an old bar count despite a corrected top-level request. Happy-path fixture success alone did not establish live readiness.

**How to apply:** Check all required response fields appear in prompts, ensure shared musical parameters agree across skill documents and requests, induce real validation failures, and assert persisted diagnostics and exact exhausted-repair counts.

Persist unapproved section/candidate evidence and review responses before running later evaluators or report-finalization checks. Freeze immutable inputs, not runtime-derived plans or output files.

**Why:** A live section experiment completed every writer, but a final freeze check treated the newly generated plan as an immutable offline input and crashed before saving the candidate. Metrics survived; the exact generated score did not.

**How to apply:** Keep candidate persistence separate from approval and promotion. Journal each successful section atomically, retain review verdicts with their candidate hash, and ensure report failures cannot erase evidence of expensive provider work.

Distinguish score length, score density, peak input context, cumulative input tokens, and output budget when assessing scale.

**Why:** A request for many bars can still start with very few source events. A large allowed context is not evidence that a genuinely large score was processed, and larger input capacity does not prevent output truncation.

**How to apply:** Report actual events and observed per-call tokens alongside bar count. Label synthetic serialization projections as estimates, and preserve full source MIDI outside summaries when considering section-based retrieval.
